# 完整报告生成规范

## 适用触发场景
当用户要求生成以下内容时使用：
- 分析报告
- 经营分析报告
- 月报
- 完整报告
- markdown 报告

---

## 必须先做的步骤

先调用 `read_file` 读取：

`/assets/financial-analysis/biz-analysis-report.md`

将读取到的模板作为结构基础，再结合实际查询数据进行填充、删减和写作。

完整报告场景下，模板填充完成后不要直接交付用户，还必须增加一步：
- 在正式输出前先做一次数据与文本自审校验
- 再依据校验结果修正成最终汇报版
- 默认只展示终稿，不展示中间校验过程
- 最终汇报版默认是“详版正式报告”，不是删减后的简版摘要
- 必须兼顾会场汇报与书面留档两种用途

自审校验时，至少要明确检查：
- 当月、累计、上月三个期间是否都已正确落文
- `fone` 与 `tuwei` 两类统计口径是否都已覆盖
- 达成率、差额、同比、完成判断是否都绑定了明确口径
- 结论是否能被文中的数据或表格直接支撑
- 是否至少保留 3 类核心数据表；数据充足时尽量保留 4 类及以上
- 若发现口径冲突、表格缺失、结论与数据不一致，必须先修正后再输出
- 是否存在明显 AI 腔、口语化表达、宣传化措辞或机械拼接段落
- 是否已经改写成管理层可直接阅读或会上可直接汇报的正式语言

## 报告主线

报告默认按以下主线生成：
1. 经营摘要
2. 年初预算完成情况总览
3. 年初预算详细分析
4. 成本分析
5. 重点项目 / 重点单元分析
6. 突围考核完成情况
7. 管理建议
8. 图表结构化配置

不要再扩展成过多无关章节，也不要为了“完整”保留大量空章节。
但也不要为了“汇报感”把核心数据、表格、对比明细、成本拆解和重点单元支撑信息删掉。

---

## 详细度要求

### 年初预算部分
这是报告的主分析模块，必须写得更详细，重点回答：
1. 整体经营情况如何
2. 当月、累计、上月分别表现如何
3. 当月与累计必须分开写，不能把达成率、差额、同比混成一个口径不明的结论
4. 与年初预算值相比差异在哪
5. 成本费用如何影响利润
6. 哪些重点项目 / 单元表现较好，哪些形成拖累
7. 当前状态对学年目标有何影响
8. 同比变化如何，背后的经营含义是什么
9. 成本章节除人力成本外，默认覆盖餐饮支出、物资销售成本、车辆费用、能耗费、差旅费、业务招待费、其他支出等费用项

### 突围考核部分
这一部分可以简写，重点强调：
1. 核心指标完成情况
2. 达成率
3. 差额
4. 是否达标

突围考核部分不要求写成长篇归因分析。

## 写作原则

报告必须体现专业财务分析能力，而不是简单的数据拼接。

每个主要章节尽量回答：
1. 结果如何
2. 为什么会这样
3. 会带来什么经营影响
4. 下一步怎么办

推荐的段落推进逻辑为：
1. 结果判断
2. 差异分析
3. 原因拆解
4. 风险提示
5. 后续动作

不要机械逐条罗列，但应尽量保证关键段落具备上述经营逻辑。

并额外满足：
- 达成率、差额、同比、完成判断都要绑定到明确口径
- 同时写当月与累计时，优先拆成两个小节或两张表
- 不要用一个“预算达成率”列同时承载当月和累计口径

若查询结果中已经返回以下字段，必须显式利用：
- `budget`
- `completion_rate`
- `diff`
- `year_over_year`

不要只使用 `actual` 做静态描述。

推荐风格：
- 简洁
- 结论先行
- 面向管理层
- 财务分析视角明确
- 具备会议汇报感，开头即可供管理层听取摘要
- 语气正式、克制，不使用口语化或宣传化表达
- 更接近财务 BP / 经营分析负责人撰写的汇报材料，而非助手式回答

推荐常用表达：
- 整体看
- 从结果看
- 具体来看
- 主要原因为
- 核心问题在于
- 需重点关注
- 后续需重点推进
- 节奏后移
- 兑现不足
- 利润转化不足
- 成本刚性偏强
- 分化
- 修复
- 改善

建议优先从以下维度做归因：
- 市场拓展
- 项目储备
- 收入确认节奏
- 毛利率变化
- 人工成本
- 费用投入
- 回款兑现
- 区域差异
- 组织协同

建议写法要尽量具体，优先使用：
- 加快兑现
- 推动闭环
- 压实责任
- 分类施策
- 专项攻坚
- 一项目一策略
- 明确节点

避免使用：
- “非常好 / 非常差 / 很猛 / 未来可期 / 显著积极”
- “可以看到 / 总的来说 / 值得一提的是”
- 无数据支撑的强结论

推荐呈现方式：
- 前部先给可直接口头汇报的经营摘要、风险与机会
- 后部保留完整正文、数据表格、重点单元对比和成本费用支撑
- 让一份材料同时满足“能讲”和“能留档”

建议默认保留的核心表：
- 核心经营指标总览表
- 年初预算达成对比表
- 成本费用分析表
- 重点项目 / 重点单元对比表
- 突围考核完成情况表

## 图表结构化配置要求

完整报告场景下，报告末尾必须追加“图表结构化配置”章节，输出 3-5 个可供前端或后处理程序消费的 chart spec JSON。

输出规则：
- 使用 `json` fenced code block
- 优先输出 3-5 个；只有整体数据明显不足时才允许少于 3 个
- 每个 chart spec 必须对应正文中已经出现的一个明确结论
- 不得输出无数据支撑的装饰性图表
- chart spec JSON 作为唯一图表交付格式，供离线脚本直接生成 PNG

每个 chart spec 至少包含以下字段：
- `id`: 唯一标识，建议 kebab-case
- `title`: 结论式标题
- `summary`: 1-2 句说明该图要表达的经营结论
- `chartType`: 如 `bar`、`line`、`stacked_bar`、`combo_bar_line`、`waterfall`、`pie`
- `scope`: 统计口径与期间，例如 `fone-monthly-202602`
- `dimension`: 横轴或分类维度，例如 `metric_category`、`month`、`node_name`、`expense_type`
- `metrics`: 图中使用的指标键数组
- `unit`: 主单位，如 `万元`、`%`、`人`
- `series`: 可直接渲染的数据序列数组

`series` 建议结构：
- `name`: 序列名称
- `type`: 序列图形类型
- `unit`: 当前序列单位
- `data`: 数据点数组

`data` 中建议至少包含：
- `label`: 类目名称
- `value`: 数值
- `target`: 可选，目标值或对照值
- `note`: 可选，补充说明

建议优先输出的图表主题：
- 核心经营指标实际 vs 预算/目标对比
- 当月 vs 上月 vs 累计的收入/利润变化
- 重点项目或重点单元贡献/拖累排序
- 成本费用结构或偏差归因
- 突围考核完成情况对比

---

## 缺失数据处理规则

若某一字段缺乏支撑数据：
- 标记为 `【待补】`
- 不得编造数据
- 不得给出过强结论

若字段可由查询结果聚合或计算得到：
- 应先聚合 / 计算后写入报告
- 不要把原本可算出的值留作 `【待补】`

若某类数据数据库暂无：
- 标记为 `【数据库暂无此数据】`
- 可直接跳过整段无效展开

---

## 建议写法提示

在数据支持的前提下，适当体现：
- 三大区域 + 商业业务是增长极
- 后勤管理中心是基本盘

应在摘要和判断中体现：
- 增长极的拉动作用
- 基本盘的稳定作用
- 成本费用对利润的侵蚀或支撑

并主动计算和体现：
- 环比变化
- 同比变化
- 预算达成率与差额
- 重点项目 / 单元的贡献度或拖累度
