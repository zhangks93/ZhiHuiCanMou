AI 经营分析 AI 场景建设大纲优化补充版
现有资产 原有流程 建设路径 数据顺序 协作模式
基于业务大纲优化 · 聚焦经营分析 AI 场景

先把月度经营分析做深，再把财务侧和运营侧连起来。

这不是重新规划一个大而全的数据平台，而是在现有经营分析看板、西南业绩总控多维表格、智汇参谋 APP 的基础上， 形成一条更清晰的建设路径：先完善经营分析报告编写，再支持下钻一层的问题分析，最后进入事中提醒。

定位：统一数据层可与采购场景一并建设；本场景重点建设业务应用层和 Agent 使用方式。应用层由业务按照 OPC 模式自建，Agent 框架充分借助 Workbuddy、Codex 等成熟 AI Coding / Agent 工具，并通过 Skill + API 接入数据与能力。

优化后的主线

  • 第一步：补强月度经营分析先把报告编写、核对、复盘的重复工作降下来。
  • 第二步：财务运营打通让收入、利润、毛利、人效问题可以继续下钻到业务驱动。
  • 第三步：按业务数据顺序纳入先食配，后费效，再食堂，最后便利店。
  • 第四步：从事后到事中先做事后分析标准化，再做事中提醒和异常预警。

一、现有资产

不是从零开始，先把三个现有资产串起来。

当前已有资产已经覆盖“看数据、沉淀表格、AI 分析”三个方向，后续建设要围绕复用和补齐，而不是重复造入口。

资产 1

经营分析看板

作为经营数据的事实入口，保留现有看板的指标展示、组织查看、期间切换和基础对比能力。

  • 短期用于月度经营分析取数核对。
  • 中期沉淀常用指标和异常阈值。
  • 长期成为 AI 分析结果的证据来源之一。
资产 2

西南业绩总控多维表格

作为区域运营分析的业务侧补充资产，适合承接更细颗粒度的经营动作和过程数据。

  • 短期由西南区域补充字段与流程。
  • 中期抽象为区域运营分析模板。
  • 长期纳入统一数据层或通过 API 供 Agent 使用。
资产 3

智汇参谋 APP

作为 Agent 交互和经营分析范式参考，复用其组织解析、层级下钻、对话分析和报告输出思路。

  • 复用经营分析 skill 与 prompt 设计。
  • 复用组织范围确认和同级对标逻辑。
  • 复用“分析过程可见、结果可追溯”的交互方式。

二、原有流程

当前流程的主要问题是人工中转太多，导致报告和会议消耗大。

1

fone 数据导出

财务先从系统侧导出经营数据，数据口径和版本依赖人工确认。

2

财务加工

进行清洗、汇总、对比、差异计算和初步判断，重复性工作较多。

3

业务核对

业务侧补充解释、确认异常、校对口径，沟通成本高。

4

单位编制报告

各单位按各自理解写月度分析，质量和颗粒度不统一。

5

经营分析月会

会议里大量时间用于解释数据和补充背景，真正决策时间被压缩。

区域运营分析待补充 西南区域运营分析建议先由业务侧补充现行流程：当前看哪些表、哪些人维护、哪些字段用于会议、哪些动作会被追踪。补齐后可作为第二条试点流程，不宜一开始和月度经营分析混在一起做。

三、拟建设路径

聚焦两个目标：报告编写更完善，问题分析能再下钻一层。

目标 1：完善经营分析报告编写

把“月度经营分析报告”拆成可标准化的模块，由 Agent 先生成草稿，业务和财务只做复核、补充和定稿。

  • 固定报告结构：本期数据、核心结论、预算/目标完成、组织贡献、成本费用、人效、风险和建议。
  • 固定证据规则：每个关键判断必须回到实际值、目标值、完成率、差额、同比或环比。
  • 固定审阅动作：财务确认口径，业务确认原因，负责人确认行动项。
  • 固定输出物：月度报告、会议摘要、异常清单、下月追踪项。

目标 2：财务侧与运营侧衔接

经营分析不止回答“差多少”，还要回答“差在哪里、为什么、下一步查什么”。

  • 收入问题下钻到业务量、价格、项目、渠道、门店或区域。
  • 利润问题下钻到毛利率、成本结构、费用执行和人效。
  • 人效问题下钻到排班、人员结构、出勤和单位产出。
  • 费用问题下钻到可控费用、费用归集、异常波动和责任动作。
数据层

统一数据层与采购场景一并建设

经营分析只消费统一数据层提供的指标、组织、权限和查询 API，不在应用层重复沉淀主数据。

应用层

业务按 OPC 模式自建

业务拥有页面、模板、流程和工作模式定义权，FDE 负责技术兜底和工程化支持。

Agent 层

Workbuddy + Skill + API

充分借助 Workbuddy、Codex 等成熟 Agent / AI Coding 工具，核心是把 Skill 和 API 设计清楚。

四、运营数据纳入顺序

按业务成熟度和经营关联度分阶段纳入。

不要一次把所有运营数据都接入。先选最能解释经营波动、最容易形成闭环的数据域。

顺序 数据域 为什么先/后做 优先解释的问题 建议产物
1 食配 和收入、成本、毛利关联最直接，适合作为财务到运营下钻的第一类数据。 收入波动、成本异常、配送履约、项目贡献。 食配经营分析模板、项目异常清单、毛利下钻卡片。
2 费效 直接服务利润、人效和费用控制，能承接管理层对“降本增效”的关注。 人力成本率、单位产出、费用超支、效率低点。 费效诊断模板、人效排行、费用预警清单。
3 食堂 经营动作复杂，涉及客流、餐次、菜品、排班和满意度，适合在前两类稳定后接入。 餐饮收入、毛利率、客流变化、排班效率。 食堂经营看板、餐次分析、异常门店复盘。
4 便利店 门店经营颗粒度细，商品结构和促销因素多，适合在平台模板成熟后复制。 门店收入、商品毛利、库存、促销效果。 便利店单店诊断、商品结构分析、低毛利预警。

五、从事后分析到事中提醒

最终状态不是只会写报告，而是能提前提醒业务。

阶段 1

事后分析标准化

先把月度经营分析报告的取数、比较、归因和建议动作标准化，减少报告出具工作量。

阶段 2

过程数据下钻

接入食配、费效、食堂、便利店等运营数据，让异常能继续追到业务过程。

阶段 3

事中提醒

把异常阈值、目标进度、费用波动和重点单位风险转成提醒、任务和会议跟踪项。

六、协作模式

FDE 做技术兜底，业务负责人定义流程边界。

FDE 职责

  • 前期确认技术架构与选型，明确统一数据层、应用层、Agent 运行层的边界。
  • 中期协助 OPC 完成自主编码工作，包括 Skill、API 接入、页面结构和任务流转。
  • 后期协助完成 Demo 到产品的工程化工作，包括权限、日志、稳定性、部署和复用机制。

业务负责人职责

  • 确认流程重塑边界：哪些环节由 AI 生成，哪些环节必须人工复核。
  • 确认工作模式改变边界：报告如何定稿、会议如何使用、行动项如何追踪。
  • 确认业务数据纳入优先级：先食配、后费效、再食堂、便利店是否符合当前试点节奏。
  • 确认经营分析成功标准：减少多少报告工作、会议时间、重复核对和人工拉数。

七、建议下一步

把方案落到一个小闭环。

1 周内

补齐西南流程

让西南区域补充区域运营分析的现有表、字段、会议动作和当前痛点。

2 周内

定义首版报告模板

先以月度经营分析为试点，固定结构、证据规则、审阅流和输出物。

3-4 周

做一个 Demo

业务用 AI Coding 搭一个任务入口，FDE 协助接 Skill + API，跑通一次报告草稿生成。

4 周后

评估是否扩展

根据报告出具时间、人工核对次数、会议准备时间和业务复用意愿决定下一阶段。
